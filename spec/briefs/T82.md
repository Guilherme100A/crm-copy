## Critérios de aceitação (SPEC.md, "### T82")
- **AC-T82-01** `POST /api/flows/:id/simulate` executa o rascunho em dry-run (mesmos handlers do motor) e devolve a transcrição das mensagens e o caminho percorrido, sem gravar runs nem chamar o gateway.
- **AC-T82-02** Respostas simuladas escolhem o handle (opção, timeout, outro, sucesso/falha) e o simulador continua a partir dele.
- **AC-T82-03** Loop ou caminho acima de 50 passos é interrompido e marcado no resultado.
- **AC-T82-04** No editor, o painel do simulador mostra a conversa em formato de chat com botões das respostas possíveis (desktop e `mobile`).

Referência 06 §4.4: o simulador fica `running`, `waiting` ou `finished`. Os tipos de espera são `wait_response`, `menu`, `smart_interval`, `condition_choice`, `carousel`, `template`, `distributor`, `ai_choice`, `integration_choice`, `kieai_choice` e `payment_choice`.

06 §5.6: o simulador oferece quick replies por handle, por exemplo "Simular timeout", opções do menu, Sucesso/Falha, saídas do distribuidor, saídas da IA e "Simular webhook (pagamento aprovado)". Ele detecta fluxo sem START, falta de próximo passo, loop curto e caminho longo demais. Nó não suportado mostra "ainda não é simulado. Seguindo." Nada é enviado nem salvo.

## O que as dependências entregaram (código na main)
### Dry-run do motor (T25): `packages/core/src/flows/engine/dry-run.ts` (exportado por `@crm/core`)
- `dryRun(input: DryRunInput): Promise<DryRunResult>`.
  - `DryRunInput = { definition, contact?, vars?, registry?, llm?, maxSteps?, timeZone?, companyId?, now? }`.
  - `DryRunResult = { status: 'completed'|'failed'|'waiting', error?, steps: DryRunStep[], sent: FakeSentMessage[], vars, wait? }`.
  - `DryRunStep = { seq, node_key, node_type, status, handle?, error? }`.
- Usa um store em memória e um `FakeWaGateway` próprio (`autoConnect`, cria a sessão sob demanda). O `repo` é `{ db: null, dryRun: true }`.
- O laço `runLoop` (`engine/runner.ts`) é o mesmo do motor:
  - `MAX_STEPS_PER_JOB = 50`; ao passar disso, `failed` com `LOOP_GUARD_ERROR = 'loop_guard'` (AC-03).
  - Um erro segue a aresta `failure`, se houver.
  - `{ wait }` para com status `waiting`.
- `FlowEngine.dryRun(ctx, { flowId, ... })` lê o **rascunho** com `new FlowStore(db).toDefinition({ companyId, userId }, flowId)` e usa o registry e o llm do motor.
  - Na API, o motor vem de `flowServices(deps).engine` (`apps/api/src/routes/flow-runs/services.ts`). Esse motor não recebe `llm` e tem um `noGateway` que lança erro; o dry-run não usa esse gateway.
- `FakeSentMessage = SendRequest & { messageId, message }` (`packages/wa-port/src/testing/fake-gateway.ts`). Monte a transcrição a partir de `sent[].content`.
- **O dry-run NÃO retoma de uma espera.** Para continuar pelo handle escolhido (AC-02), a rota pode rodar `dryRun` de novo:
  - use uma cópia da definição com `entry` = destino da aresta `(nó, handle)`;
  - repasse `vars`;
  - conte os passos acumulados, para que o limite de 50 valha no caminho todo.
  - Combine o protocolo stateless (por exemplo, o cliente reenvia `{ node_key, handle, vars, steps_so_far }`) e documente-o no relatório.
### Comportamento dos nós no dry-run (código aberto)
- **Lógica (T41)**, `nodes/logic/handlers.ts`: sem banco, usa o fuso padrão. Sem banco, o distribuidor escolhe `output:<id>` por conta própria (linha ~130), mas o simulador deve oferecer a escolha.
- **Mensagens (T51)**, `nodes/messaging/data.ts`: sem banco, envia para a sessão `DRY_RUN_SESSION = 'dry-run'`. `defaultGlobals` devolve `{}`, ou seja, as variáveis globais não são aplicadas.
- **Interativos (T62)**, `nodes/interactive/handlers.ts`: devolvem `{ wait: { ...waitForReply(...), reentry: true } }` com handles `option:<id>`, `other` e `timeout`. Ao retomar, o nó reexecuta e lê `vars.__replies` (`FlowControl.resolveReply` em `engine/control.ts`).
- **CRM (T63)**, `nodes/crm/handlers.ts:50`: `dbOf()` lança `CrmNodeError('dry_run', …)`, então no dry-run o nó segue `failure` ou falha.
- **Externos (T42)**, `nodes/external/handlers.ts`:
  - `integration` chama `safeHttpRequest` **de verdade**, sem checar `dryRun`;
  - `ai` usa `deps.llm ?? ctx.llm`.
- **Pixel/Pagamento** (`nodes/pixel`, `nodes/payment`): checam `ctx.repo.dryRun` e seguem em frente (`chargeCreated`).
- **Handles:** `@crm/shared/flows` exporta:
  - `nodeHandles(node)`, que lista os handles de saída de um nó;
  - `handle.*` (`source`, `timeout`, `other`, `failure`, `success`, `option(id)`, `output(key)`);
  - `parseHandle` e `isWaitingHandle(nodeType, value)`.
  Use esses helpers na API e na web para montar os botões.
### Editor (T45)
- `apps/web/src/features/flow-editor/canvas/editor.tsx` (`FlowEditorPage`): o cabeçalho tem os botões `flow-pause`, `flow-activate` e `flow-properties-toggle` (`lg:hidden`). O canvas usa `data-testid="flow-canvas"`.
- `canvas/api.ts`: `bundleQuery(id)` → `GET /api/flows/:id/editor-bundle` e `flowApi.save` → `PUT /api/flows/:id/definition`. HTTP: `api` de `@/lib/http`.
- Permissões (`packages/shared/src/permissions/catalog.ts`): `flows.view|edit|delete|run`. O member tem só `view` (06 §8). Simular não grava nada; sugestão: `requirePerm('flows.view')`, decisão a registrar nas Notas.

## Atenção (achados do levantamento)
1. **O botão "Simular" e o painel estão fora dos Paths.** O ponto de montagem é o cabeçalho de `apps/web/src/features/flow-editor/canvas/editor.tsx`, que pertence à T45 e não está em `SHARED_PATHS`. Peça ao Orquestrador a liberação aditiva de `editor.tsx`, para uma linha de botão e o import do painel, ou reporte BLOCKED.
   - **Risco de sobreposição com a T93 (copiloto),** que precisa do mesmo cabeçalho.
2. **Nunca chame a rede no simulador.** No dry-run, o nó `integration` faria o HTTP real e o `ai` chamaria o LLM, se houvesse um. Monte na rota um **registry do simulador**, a partir de `createNodeRegistry()` + `register(...)`:
   - `integration` e `ai` viram escolhas (`integration_choice`, `ai_choice`): o handler devolve `{ wait }` com os handles de `nodeHandles(node)`;
   - os nós de CRM (`tags`, `kanban`, `department`, `chat_controller`, `manipulator`, `approved_sale`, `ai_agent`), `pixel` e `payment` seguem com aviso "ainda não é simulado. Seguindo." (06 §5.6), em vez de `failure`.
3. **Distribuidor e condição** decidem sozinhos sem banco. Para o AC-02 ("outro, sucesso/falha"…), transforme-os em escolha (`distributor` e `condition_choice` em 06 §4.4).
4. **Retomada após resposta:** os interativos usam `reentry`. O simulador deve repassar a escolha como handle e seguir a aresta, sem reexecutar o nó.
5. **Fluxo sem START / sem próximo passo:** `definition.entry` pode faltar no rascunho. Devolva um aviso no resultado, sem 500.
6. **Rota:** `POST /api/flows/:id/simulate` fica no módulo `flow-simulate`, montado em `/` com caminho absoluto, como as demais rotas.
   - Fluxo de outra empresa → 404 (`FlowStoreError` → `ApiError`, ver `routes/flows/index.ts`).
   - Corpo validado com zod → 422.
7. **Overlap:** a T56 e a T57 estão IN_PROGRESS em `node-editors/**` (registry com `import.meta.glob`). Não toque no `registry.ts` dos editores.
